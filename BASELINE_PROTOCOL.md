# Baseline Administration Protocol v0.1

## Purpose

The Software Development baseline exists to discover my current capability and important knowledge gaps.

It is not:

- a certification exam
- an interview score
- a ranking
- a test I am expected to "win"

The goal is accurate evidence that can guide what I should learn next.

---

# Baseline Structure

The broad-screen baseline begins with two provisional sessions.

## Session A — Programming Capability

Primary task families:

1. Read / Trace / Explain
2. Independent Build
3. Debugging
4. Problem Decomposition

Main purpose:

- programming reasoning
- code understanding
- application
- debugging
- decomposition
- prerequisite signals

## Session B — Web and Development Foundations

Primary task families:

1. Web reasoning
2. Front-end foundations
3. Development workflow / data / testing
4. optional DSA probe

The exact structure may adapt based on evidence from Session A.

---

# Fresh Task Rule

Exact baseline questions must not be stored or shown before the attempt.

Tasks should be generated fresh when administered.

Reassessment should use changed variants rather than simply repeating solved tasks.

---

# Initial Attempt Rule

When unaided ability is being measured, begin with:

**R0 + A0**

Meaning:

- no external reference
- no instructional assistance

The initial result must be preserved before assistance is introduced.

---

# Reference-Allowed Tasks

Some tasks may explicitly allow:

**R1 + A0**

Examples:

- official documentation
- API reference
- command syntax lookup

Reference use is acceptable when memorizing exact syntax is not the capability being tested.

The task must state whether references are allowed.

---

# AI Rule

During an R0 + A0 diagnostic attempt:

Do not use:

- ChatGPT
- Claude
- Copilot
- AI search or AI code generation
- AI debugging assistance

After the independent result has been captured, instructional assistance may be introduced for diagnosis.

---

# Assistance Escalation

If the learner becomes stuck:

1. preserve the independent result
2. determine whether further unaided work is useful
3. introduce the smallest useful assistance

Possible progression:

A1 — Orientation  
A2 — Small hint  
A3 — Guided scaffolding  
A4 — Substantial solution exposure

The lowest assistance level that enables meaningful progress should be recorded.

---

# Clarification Rule

Neutral clarification does not count as instructional assistance.

Examples:

- explaining ambiguous wording
- clarifying expected input/output
- correcting a typo in the task

If clarification reveals:

- the concept being tested
- the solution strategy
- the bug location
- the implementation path

then it must be recorded as instructional assistance.

---

# Think-Aloud Rule

The learner does not need to narrate every thought.

However, for diagnostic value, the coach may ask for brief reasoning such as:

- expected behavior
- current hypothesis
- planned approach
- reason for a decision
- explanation after a fix

The goal is useful evidence, not constant narration.

---

# Documentation of Evidence

For each meaningful task, LearningOS should preserve where relevant:

- task family
- primary skill
- supporting skills
- evidence type
- result
- reference use
- instructional assistance
- meaningful attempts
- error / gap signals
- task novelty
- diagnostic mode
- artifact/code
- follow-up requirement

The learner should not manually fill out a large form.

The coach should derive most of this evidence.

---

# Result Interpretation

Possible task results:

- Pass
- Partial
- Fail

Result alone is insufficient.

Interpret it with:

- reference use
- instructional assistance
- explanation quality
- novelty
- evidence type
- observed process

Example:

Pass at R0 + A0

is different evidence from:

Pass after A3.

---

# Gap Rule

One failure is normally a signal, not a confirmed gap.

Possible progression:

Signal  
→ Suspected Gap  
→ Confirmed Gap

A gap becomes more credible when evidence:

- repeats
- appears across different tasks
- survives feedback
- appears in multiple evidence dimensions
- reappears after delay

---

# Stop Rule

Do not keep testing simply to generate more data.

Stop probing an area when:

- strong evidence is sufficient
- a useful gap has already been identified
- additional same-day testing is unlikely to change the learning decision
- the area is currently low priority
- fatigue is reducing evidence quality

---

# Difficulty Adaptation

Do not automatically begin with absolute beginner tasks.

Start at a level capable of distinguishing:

- fragile understanding
- functional working ability
- stronger independent capability

If a task is clearly too easy:

increase difficulty.

If a task fails because of a clear prerequisite:

probe the prerequisite.

If a result is ambiguous:

use a different evidence format.

---

# Fatigue Rule

The baseline does not need to finish in one sitting.

If concentration or effort quality noticeably drops:

stop.

Continue in another session.

Poor performance caused mainly by fatigue should not be interpreted as a stable knowledge gap.

---

# Coach Behavior During Baseline

The coach must not:

- accidentally reveal the answer before the initial attempt
- praise mastery without evidence
- interpret one failure as overall programming weakness
- treat documentation use as cheating when it is allowed
- optimize for completing the task instead of measuring ability

The coach should:

- keep instructions clear
- protect baseline integrity
- capture evidence
- ask targeted diagnostic questions only when useful
- escalate assistance gradually
- stop when sufficient evidence exists

---

# After Session A

The coach should produce a provisional evidence map containing:

## Strong Signals

Areas showing useful independent evidence.

## Working / Needs Strengthening

Areas where some ability is present but evidence is incomplete or fragile.

## Suspected Gaps

Patterns requiring another probe or targeted learning.

## Confirmed Gaps

Only when evidence is sufficiently strong.

## Unknown / Untested

Areas where evidence is insufficient.

## Dependency Signals

Possible prerequisite weaknesses.

## Assistance Signals

Areas where performance changes substantially with instructional assistance.

---

# Important Limitation

The first baseline cannot establish Retained status for newly tested skills.

Retention requires meaningful delayed evidence.

A baseline may produce:

- Working
- Solid-now

but retention remains untested unless suitable historical or delayed evidence exists.

---

# Pilot Rule

This protocol is frozen enough for the v0.1 pilot.

Do not redesign it during Session A because of minor inconvenience.

Record problems and revisit the protocol after meaningful pilot evidence exists.
